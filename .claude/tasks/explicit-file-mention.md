# Задача: Приоритет явно названного файла в retrieval

## Контекст

Пользователь спросил "расскажи подробнее про docker-compose.prod.yml" и
получил ответ по обрывкам из `DEPLOY.md`, а не по самому файлу — `DEPLOY.md`
упоминает "docker-compose" в прозе и обошёл реальный YAML-файл в top-K
после RRF-фьюжна и реранкинга (`RERANK_TOP_K = 5` в `api/routers/ask.py`).
Явно названный файл ничем не защищён от вытеснения — генерик top-K не
даёт гарантий, что все чанки одного файла выживут.

Рассматривался вариант с regex-извлечением "похожих на имя файла" токенов
из вопроса — отклонён: ненадёжен на естественном языке (ложные
срабатывания на версиях/доменах, ложные пропуски на нестандартных именах).
Вместо этого сверяемся с уже известным списком проиндексированных путей
репозитория — только реальные имена, никакого угадывания по паттерну.

## Что нужно реализовать

`api/services/retrieval.py`:

1. `find_mentioned_file_chunks(db, repo_id, question) -> list[RetrievedChunk]`
   — публичная функция:
   - `_list_indexed_file_paths` — все уникальные `file_path` репозитория
     (один запрос, индекс `idx_chunks_repo_file` уже есть)
   - `_find_mentioned_file_path` — чистая функция без БД: basename каждого
     пути ищется как подстрока в вопросе (case-insensitive); при
     коллизии одинаковых basename в разных директориях — предпочесть
     совпадение, чей полный путь тоже встречается в вопросе, иначе взять
     путь с наименьшей глубиной вложенности
   - `_load_file_chunks` — все чанки найденного файла по порядку
     `start_line`, с лимитом `MAX_PINNED_FILE_CHUNKS = 5` (та же защита от
     раздувания контекста, что `OPENAI_MAX_INPUT_TOKENS` в
     `embeddings.py` и `FALLBACK_CHUNK_LINES` в `chunking.py`)

`api/routers/ask.py`:

2. Перед реранком — получить `pinned_chunks` через
   `find_mentioned_file_chunks`. Убрать их из кандидатов на реранк по
   `id` (иначе задвоятся), уменьшить `top_k` реранка на количество
   pinned-чанков (но не ниже 1 — совсем без общего контекста уходить не
   стоит). Итоговый список — `pinned_chunks + reranked_chunks`,
   pinned гарантированно попадают в ответ, а не соревнуются за место.

## Критерии готовности

- [ ] Вопрос, называющий реально проиндексированный файл — все его чанки
      (до лимита) попадают в контекст ответа, даже если другой файл
      обошёл бы их по реранк-скору
- [ ] Вопрос без явного упоминания файла — поведение не меняется
      (пустой `pinned_chunks`, `top_k` реранка как раньше)
- [ ] Коллизия одинаковых basename в разных директориях — не падает,
      выбирает наименее произвольный вариант
- [ ] `api/routers/ask.py`'s существующие тесты (без упоминания файла в
      вопросе) проходят без изменений — pinned-логика не меняет поведение
      при пустом результате поиска

## Не делать

- Не делать это через regex по вопросу — сверяемся только с реальными
  путями репозитория
- Не трогать `hybrid_search`/`rerank`/`chunking.py` — pinned-логика живёт
  рядом, не заменяет существующий pipeline
