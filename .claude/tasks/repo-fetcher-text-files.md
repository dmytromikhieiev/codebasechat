# Задача: Индексировать не только код, но и текстовые/конфиг-файлы

## Контекст

Пользователь заподозрил баг: "не индексирует файлы верхнего уровня, не
вложенные". Диагностика показала, что дело не в глубине пути, а в типе
файла — `api/services/repo_fetcher.py::_extract_code_files` изначально
(см. [[repo-fetcher]]) отбрасывал любой файл без распознанного языка
(`detect_language` вернул `None`), то есть `README.md`, `PLAN.md`,
`CLAUDE.md`, `docker-compose.yml`, `requirements.txt`, `Dockerfile*` и
т.д. никогда даже не попадали в `fetch_repo_files`, не то что в чанкинг.
Так как в типичном репозитории корень набит именно такими файлами, а
вложенные пути — в основном код, баг выглядел как "верхний уровень не
индексируется".

Это было осознанным решением в исходном ТЗ (`repo-fetcher.md`:
"файлы без распознанного языка ... не попадают в результат"), а не
регрессией. Пользователь явно попросил расширить индексацию на
README/конфиги/доки — эта задача меняет то прежнее решение.

Побочный эффект: fallback-чанкинг в `chunking.py` (`language=None` →
построчные чанки, `FALLBACK_CHUNK_LINES`) был реализован и покрыт
тестами с самого начала, но фактически ни разу не вызывался в проде —
`repo_fetcher` отсекал такие файлы до чанкинга. Эта задача делает его
наконец достижимым.

## Что нужно реализовать

`api/services/repo_fetcher.py`:

1. `TEXT_FILE_EXTENSIONS` — расширения, которые стоит индексировать даже
   без распознанного языка программирования (`.md`, `.mdx`, `.rst`,
   `.txt`, `.yml`, `.yaml`, `.json`, `.toml`, `.ini`, `.cfg`, `.sql`,
   `.sh`, `.env.example`)
2. `TEXT_FILE_NAMES` — точные имена файлов без расширения по тому же
   принципу (`Makefile`, `LICENSE`, `.gitignore`, `.dockerignore`, ...),
   плюс отдельная проверка `basename.startswith("Dockerfile")` — в этом
   репозитории Dockerfile'ы называются `Dockerfile.api`/`Dockerfile.worker`/
   `Dockerfile.frontend`, обычный `endswith`-чек их не поймает
3. `EXCLUDED_FILE_NAMES` — сгенерированные лок-файлы по точному имени
   (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `poetry.lock`,
   `Pipfile.lock`, `composer.lock`, `Gemfile.lock`, `go.sum`,
   `Cargo.lock`) — исключены явно, даже несмотря на то что их расширение
   (`.json`/`.yaml`) само по себе прошло бы фильтр текстовых файлов;
   генерируются автоматически, огромные, не несут смысла для чата
4. `_extract_code_files`: файл проходит, если `detect_language()` вернул
   язык **или** файл проходит `_is_text_file()`; в любом случае —
   `EXCLUDED_FILE_NAMES` отсекает файл раньше этой проверки.
   `RepoFile.language` для текстовых файлов — `"text"`

## Критерии готовности

- [ ] `README.md`, `docker-compose.yml`, `package.json`, `.gitignore`,
      `Dockerfile.api` — попадают в `fetch_repo_files`
- [ ] `package-lock.json`, `yarn.lock`, `go.sum` — не попадают, несмотря
      на то что их расширения формально текстовые
- [ ] Картинки/бинарники (`.png` и т.п.) — по-прежнему не попадают
- [ ] `worker/indexer.py` не менялся — `chunk_file()` сам пересчитывает
      язык по пути и уже умеет строчный fallback-чанкинг для
      `language=None`, `RepoFile.language` этим кодом не используется

## Не делать

- Не трогать `chunking.py` — построчный fallback уже реализован и
  протестирован, этой задаче нужно только сделать его достижимым
- Не индексировать бинарные форматы (картинки, шрифты и т.д.) — они и так
  отсекаются по недекодируемости UTF-8, дополнительный whitelist не нужен
- Не расширять список поддерживаемых языков программирования — это
  отдельная тема ([[chunking]])
