# Задача: Ручной триггер реиндексации

## Контекст

Webhook URL — опциональное поле при создании GitHub App, для локальной
разработки без публичного адреса (`ngrok`/`smee.io`) его можно не
настраивать. Взамен автоматического обновления по `push` — кнопка/эндпоинт,
запускающий тот же путь, что и `.claude/tasks/webhooks.md`, но по запросу
пользователя, а не по событию от GitHub.

## Что нужно реализовать

`api/routers/repos.py` — `POST /api/v1/repos/{repo_id}/reindex`:
- 404, если репозиторий не найден или не принадлежит текущему пользователю
  (`get_current_user`)
- 409, если `repo.status == "indexing"` (уже выполняется)
- если `repo.last_indexed_sha` пуст — полный реиндекс (`enqueue_indexing_job`)
- иначе — резолвит текущий HEAD ветки (`github_app.resolve_ref_to_sha`) и
  сравнивает с `last_indexed_sha`:
  - совпадают → ничего не ставить в очередь, вернуть `up_to_date`
  - отличаются → инкрементальный реиндекс (`enqueue_incremental_indexing_job`),
    как при вебхуке, только `base`/`head` берутся не из payload, а
    резолвятся здесь

## Критерии готовности

- [ ] 401 без сессии, 404 на чужой/несуществующий repo_id
- [ ] 409 при повторном вызове, пока предыдущая индексация не завершилась
- [ ] Репозиторий без `last_indexed_sha` → полный реиндекс
- [ ] `last_indexed_sha` совпадает с текущим HEAD → `up_to_date`, ничего не
      поставлено в очередь (не тратим впустую RQ-job)
- [ ] `last_indexed_sha` отличается от HEAD → инкрементальный реиндекс с
      правильными `base`/`head`

## Не делать

- Не защищаться от двойного клика между постановкой job и тем, как воркер
  реально возьмётся за него (repo.status ещё "ready" в этот момент) —
  отдельный enum-статус под это не заводим, известное ограничение
- Не трогать webhook-флоу — переиспользуем те же `enqueue_*` функции
