# Задача: Полноценный BM25 через ParadeDB pg_search

## Контекст

Текущий BM25-канал в [[retrieval-and-answer]] (`api/services/retrieval.py::_bm25_search`)
работает через `to_tsvector('english', content)` — это не настоящий BM25
(Postgres `ts_rank` — своя эвристика по весам лексем), а `english`-словарь
стеммит и не разбивает идентификаторы: `foo_bar`/`camelCase` остаются
целым лексемом, поэтому запрос на подстроку идентификатора не находит
совпадение через BM25 (может повезти через вектор, но не гарантированно).

Это же — одна из причин, почему понадобился [[explicit-file-mention]]
(`find_mentioned_file_chunks`): раз лексический канал не даёт надёжного
точного совпадения по имени файла, пришлось городить отдельный обходной
путь по списку известных путей репозитория. Но он закрывает только
*имена файлов* — тот же класс проблемы для имён функций/классов
(`function_name` в `chunks`) не решён.

Альтернатива — ParadeDB (`pg_search`) — Postgres-расширение поверх
Tantivy: настоящая BM25-формула, настраиваемые токенизаторы (`raw`/
`whitespace`/`ngram` вместо `english`-стемминга) и field-boosting
(`file_path`/`function_name` выше `content` одним запросом).

**Важно — блокер, а не техническая деталь**: `pg_search` (ParadeDB
Community) — AGPL-3.0. Для сервиса, к которому пользователи подключаются
по сети (см. PLAN.md — "пользователь подключает свой GitHub-репозиторий"),
AGPL требует раскрытия исходного кода всего взаимодействующего по сети
сервиса, если не куплена Enterprise-лицензия у ParadeDB. Это решение
не техническое — нужно явное подтверждение от владельца продукта
**до** начала реализации, не после.

## Что нужно реализовать (только после подтверждения лицензии)

1. **Docker**: заменить базовый образ Postgres в `docker-compose.yml` на
   `paradedb/paradedb` (тот же Postgres, но с предустановленными
   `pg_search`/`pgvector`) для сервиса БД. Другие сервисы не трогать.
2. **Alembic**: новая ревизия (не редактировать `0001_init.py`) —
   `CREATE EXTENSION IF NOT EXISTS pg_search;` и
   `CREATE INDEX idx_chunks_bm25 ON chunks USING bm25 (id, content, file_path, function_name) WITH (key_field='id')`.
   Проверить руками (как требует `CLAUDE.md` для `--autogenerate`), т.к.
   это raw DDL, а не autogenerate.
3. **`api/services/retrieval.py`**: `_bm25_search` — переписать на
   `content @@@ query` / `paradedb.score(id)` вместо `to_tsvector`/
   `ts_rank`; настроить токенизатор без `english`-стемминга для `content`
   и boost на `file_path`/`function_name`.
4. **Пересмотреть `find_mentioned_file_chunks`**: если field-boosted
   точный поиск по `file_path` покрывает тест-кейс из
   [[explicit-file-mention]] не хуже — упростить/убрать pinned-логику в
   `api/routers/ask.py`. Не убирать, пока новый путь не проходит тот же
   тест на явно названный файл.
5. **RRF-фьюжн** (`_reciprocal_rank_fusion`) — оставить как есть в Python.
   Нативный hybrid-запрос ParadeDB (BM25 + вектор в одном SQL) требует
   `pgvector`, а векторы репозитория живут в Qdrant — перенос векторного
   хранилища в эту задачу не входит.

## Результат (что решили по ходу реализации)

- **Токенизатор**: не `raw`/`whitespace`/`ngram` из черновика задачи, а
  `source_code` — единственный из проверенных вариантов, который реально
  бьёт `foo_bar`/`camelCase`/пути на подтокены, сохраняя при этом
  целословное совпадение. Применён к `content`, `file_path` и
  `function_name` — все три поля дают отдачу от подтокенового поиска
  (пути и имена файлов ничем не отличаются от идентификаторов в этом
  смысле).
- **Boost-факторы**: `file_path` ×3, `function_name` ×2, `content` — базовый
  вес (без явного фактора). Подобраны на глаз, не откалиброваны количественно.
- **`CREATE EXTENSION pg_search` требует `CASCADE`**: control-файл
  расширения объявляет `vector` (pgvector) обязательной зависимостью, хотя
  в проекте векторное хранилище — Qdrant, а не Postgres. `vector`
  устанавливается как побочный эффект и не используется — безвредно, но
  стоит иметь в виду при следующем аудите установленных расширений.
- **`shared_preload_libraries=pg_search` обязателен** — `pg_search`
  регистрирует собственный WAL resource manager и не грузится через одно
  только `CREATE EXTENSION`; без этого флага сервер не даёт создать
  BM25-индекс.
- **`shared_buffers` пришлось поднять** с унаследованных 400KB (низкое
  значение уже было в существующем `./data/postgres`, не связано с этой
  задачей) до 128MB — сборка BM25-индекса на реальных данных падала с
  `no unpinned buffers available` на дефолтном значении.
- **Образ — `paradedb/paradedb:latest-pg16`, не `:latest`**: `:latest`
  собран на Postgres 18, что несовместимо с форматом каталога данных
  существующего bind-mount'а `./data/postgres` (был инициализирован под
  Postgres 16) — потребовал бы `pg_upgrade`. `:latest-pg16` пришёл
  безопасно, без миграции данных.
- **`find_mentioned_file_chunks` — решено оставить**, не упрощать и не
  убирать. `test_ask_pins_explicitly_mentioned_file_over_reranked_chunks`
  мокает `hybrid_search` целиком и проверяет только сам механизм пиннинга
  — он не показывает, устоял бы новый BM25-boost в реальном
  `hybrid_search` → RRF → rerank без пиннинга в исходном сценарии
  (`DEPLOY.md` обходит `docker-compose.prod.yml` по словам в прозе). Такой
  тест не строился — риск регрессии выше цены оставить дешёвый
  детерминированный пиннинг рядом с улучшенным BM25-каналом.

## Известные ограничения (сознательно не решаем сейчас)

- Векторное хранилище остаётся в Qdrant — не переносим на `pgvector`,
  поэтому нативный hybrid-запрос ParadeDB не используется, RRF остаётся
  в Python
- Используем только ParadeDB Community — Enterprise-функции
  (partitioned indexes, hot-standby search) не нужны на этом масштабе
